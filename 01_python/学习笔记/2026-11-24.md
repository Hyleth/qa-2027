## 二、SQLite 是什么、怎么用

### 是什么

一个"单文件数据库"：不用装、不用启动服务、不用账号密码，整个数据库就是一个文件（`test.db`）。
Python 自带 `sqlite3` 模块，一行都不用装。练 SQL 就用它，语句和 MySQL 几乎一样。

### 三步用法

```python
import sqlite3

conn = sqlite3.connect("test.db")   # ① 打开/新建数据库文件
cur = conn.cursor()                 # ② 拿"游标"，执行 SQL 的手
cur.execute("SQL语句")             # ③ 执行 SQL
conn.commit()                       # 提交，数据才写进文件
cur.fetchall()                      # 取出查询结果
conn.close()
```

### 关键点

- `IF NOT EXISTS`：建表时带上，表已存在就不会报错
- `DELETE FROM 表`：清空表，防止重复跑时数据翻倍
- `conn.commit()`：**不提交数据等于白插**
- `REAL`：金额用的小数类型（练语法用这个就行）

## 三、JOIN（拼接两张表）

### 是什么

把两张表按某个关联字段拼起来。订单表只存 `user_id`（数字），要看人名得 JOIN 用户表。

### 语法

```sql
SELECT 表A.列, 表B.列
FROM 表A
JOIN 表B ON 表A.某列 = 表B.某列
```

- `FROM`：从哪张表出发
- `JOIN`：接哪张表
- `ON`：拼接规则（等号成立才配成一行）

### 自己写的（改对了一个拼写错 FORM→FROM）

```python
print("订单+人名:", cur.execute(
    "SELECT ORDERS.ID, USERS.NAME FROM USERS JOIN ORDERS ON USERS.ID = ORDERS.USER_ID"
).fetchall())
# [(1, '张三'), (2, '张三'), (3, '李四'), (4, '王五')]
```

### 要点

- JOIN 是逐行配对的，一对多就会重复（张三两笔单 → 出现两次）
- 两张表同名的列（都叫 id）必须带表名前缀，写 `users.id` 不能光写 `id`
- 默认是"内连接"：配不上对的行会被丢掉

## 四、GROUP BY + 聚合函数（分组统计）

### 是什么

把"某列值相同"的行归成一组、压成一行，配聚合函数算统计。分组是骨架，聚合是血肉。

### 聚合函数

| 函数 | 干什么 |
|---|---|
| `COUNT(*)` | 数这一组有几行 |
| `SUM(列)` | 把这一列加起来 |

`AVG()`（平均）、`MAX/MIN()`（最大最小）用法一样。

### 语法

```sql
SELECT 分组列, 聚合函数
FROM 表
GROUP BY 分组列
```

### 自己写的

```python
print("每人订单数:", cur.execute(
    "select u.name, count(*) from users u join orders o on u.id = o.user_id group by u.name"
).fetchall())
# [('张三', 2), ('李四', 1), ('王五', 1)]
```

### 铁律（必须记住）

`SELECT` 里的列，**要么在 `GROUP BY` 里，要么被聚合函数包着**，不能有"裸列"。

---

## 五、HAVING（分组后过滤，今天的合格线）

### 是什么

分组**之后**再筛选。`WHERE` 在分组**前**过滤原始行，`HAVING` 在分组**后**过滤聚合结果。

### 为什么"总金额>100"不能用 WHERE

总金额是 `SUM()` 算完才有的数字，原始每一行里根本没有，所以 WHERE 算不了，只能 HAVING。

### 自己写的（合格线）

```python
print("总金额>100的用户:", cur.execute(
    "select u.name, sum(o.amount) from users u "
    "join orders o on u.id = o.user_id group by u.name having sum(o.amount) > 100"
).fetchall())
# [('张三', 230.0), ('李四', 200.0)]
```

这条同时用上 JOIN + GROUP BY + SUM + HAVING，是今天全部内容的合体。

## 六、表别名（自己冒出来的进阶写法）

`FROM users u` 就是给表起别名 `u`，之后全程用 `u` 代替 `users`。只在这一句里有效，起了别名后原表名不能再用。

## 九、下午：GitHub Actions（完成）

### 三要素（指着 ci.yml 能讲出来）

| 要素 | 行号 | 一句话 |
|---|---|---|
| `on` | 18 | 什么时候跑（push main / pull_request / workflow_dispatch） |
| `jobs` | 26 | 跑什么（本文件 1 个 job：`api-tests`，显示名「接口自动化（02_api）」） |
| `steps` | 39 | 怎么跑（5 步：拉代码 → 装Python3.13 → 装依赖 → pytest → 打印环境） |

- job 有两样东西：`api-tests` 是英文标识（代码/徽章用），`name:` 是中文显示名
- 门禁本体是 `run: pytest -q` 那一步——pytest 有 1 条 failed 就退出码非 0，job 红，PR 合不进去，不用另写 if

### 三种触发方式

| 触发 | 什么时候 | 用途 |
|---|---|---|
| push main | 往 main 推代码 | 日常门禁 |
| pull_request | 提 PR | 合之前先验证会不会把 main 搞红 |
| workflow_dispatch | 网页手点 | 调试时不用空提交 |

### ci.yml 是谁写的

是自己手动写的配置文件，**不是装 git 自动生成的**。git 只管版本管理，CI 是 GitHub 额外服务，得写清单告诉它怎么跑。本项目的 ci.yml 是教材阶段写好的，目标是"看得懂 + 能改"，不是"从零默写"。

### Git 团队协作完整流程（今天理清的）

```
① git clone <仓库地址>             # 一次性：拉团队代码
② git switch -c feat/xxx           # 建自己的功能分支
③ 改代码 → add → commit
④ git push -u origin feat/xxx      # 推 feat 分支（不是 main）
⑤ 网页开 PR → review → 通过         # 远程合并进 GitHub 的 main
⑥ git switch main && git pull      # 本地 main 同步远程
⑦ git switch feat/xxx && git merge main  # 把最新 main 并进 feat（易漏！）
⑧ 回到 ③ 继续下一轮
```

- **本地 merge（自己敲命令）** vs **PR merge（网页点按钮，别人 review）** 是两码事
- 单人开发直接推 main 最省事；团队协作才走 PR

### 结果：CI 绿灯

`git push -u origin main` 成功（本地 562391a → 远程 eb813d3），触发 CI，Actions 页面显示**绿色 ✓，耗时 19s，22 条用例在 Linux 上跑通**。第一次上 Linux 没有踩到 CRLF/GBK 的坑（纯 Python + pytest 项目）。

### 踩的坑

1. 第一次 push 报 `Connection was reset`——网络波动，重试就通，不是操作问题
2. GitHub 网页下午高峰直连慢，需登录才能看 Actions，卡顿时可换时间看（CI 记录不会丢）

## 十、今天的追问：真实项目的「测试环境」怎么管理（自己理解出来的，面试重点）

### 起因：这次 CI 为什么能绿灯？

因为 mock 服务和测试代码在同一个仓库，CI 机器上直接把 mock 起起来，跑的是本机 127.0.0.1，不依赖外部环境。真实项目的被测系统不在 CI 机器上，问题就浮出来了。

### 核心矛盾（自己发现的）

mock 和真实被测系统是两码事：

| | mock 服务 | 真实被测系统 |
|---|---|---|
| 是什么 | 手写的假服务，几百行 | 团队几十人写的真服务，几十万行 |
| 测什么 | 测测试框架本身对不对 | 测真实业务功能 |

**mock 不是"把公司项目塞进 mock"，而是"用假的替代真的"**——在你没权限连真实环境、或环境不稳时，先用一个行为正确的假服务把测试框架搭好。进真实项目后，把 mock 换成真实 base_url，测试代码基本不动。

### 真实项目的测试环境在「内网」，GitHub Actions 的云机器访问不到

- GitHub Actions 的机器在 GitHub 云上，和公司内网是两张网
- 真实项目的测试环境是**一台团队共享的测试服务器**，不是某人电脑上的地址

### 三种解法（按常见程度）

| 方式 | 怎么做 | 能访问内网吗 | 该懂的程度 |
|---|---|---|---|
| mock | 测试代码自带假服务 | 跑在本机 | 会用，知道是"隔离依赖" |
| 自建 CI（GitLab CI / Jenkins） | 公司内网服务器跑 CI，和测试环境同网 | ✅ | 会写配置、看绿红（换皮版 Actions） |
| Docker 现场起环境 | 打包成容器现场启动，测完销毁 | ✅ 现场搭的 | 懂概念和好处，不用动手 |

**核心认知：GitLab CI 和 GitHub Actions 是同一类东西，只是换了厂商**。今天学的 on/jobs/steps 三要素思想通用，GitLab 只是关键字长得不同。

### Docker 到底是什么（自己追问到底，彻底搞清）

- Docker 一词指三样东西，别混：

| 名称 | 是什么 | 长什么样 |
|---|---|---|
| Docker 软件 | 跑容器的程序 | 装在机器上的软件（像 Python） |
| 镜像 Image | 环境模板 | 是文件，存硬盘/镜像仓库 |
| 容器 Container | 镜像启动后的实例 | 正在跑的进程，不是文件 |

- 类比：Docker 软件 ≈ 装好的 Python；镜像 ≈ .py 文件；容器 ≈ `python xxx.py` 跑起来的进程
- **公司里不是"一个 Docker 大家共用"，而是"每台要跑容器的机器各装一个 Docker 软件"**
- 拿的是**镜像**，不是"整个 Docker"。镜像传镜像仓库，任何人 `docker pull` 下载 + `docker run` 启动，就能在自己电脑跑出一模一样的环境。前提：那台电脑装了 Docker 软件、能联网拉镜像
- Docker 解决的根本问题：**环境一致性**——"我电脑能跑、你电脑不能跑"消失

### 我该怎么用 Docker 跑接口测试（自己的完整理解，正确）

```
① 接口脚本写好
② 本地/CI 机器装了 Docker 软件
③ 开发把被测服务打包成镜像，传到镜像仓库
④ docker pull 拉镜像 → docker run 启动成容器
⑤ 被测系统 + 依赖环境完整跑在容器里
⑥ 测试脚本 base_url 指向容器地址（如 http://localhost:8080）
⑦ 直接跑脚本
```

- 实际常需两个容器一起：被测服务 + 数据库，Docker 能让它们组网
- 好处点出来：环境由开发打包固定，测试环境和开发环境一致，避免"我这边跑不通是不是环境问题"的扯皮

### 面试能直接说的答案

> 「我的练习项目用 mock 隔离了环境依赖，保证框架在任何机器能独立复现。真实项目里测试环境通常在内网，CI 用公司自建的 GitLab CI/Jenkins（同网直接访问），或用 Docker 把被测服务打包成容器现场起一套、测完销毁保证一致性。这两种思路我都了解，mock 是它们的最简版。」
