## 二、自己写用例的核心：三层断言

一条用例分三层检查响应：

| 层 | 断什么 | 为什么 |
|---|---|---|
| ① HTTP 状态码 | `status_code == 200` | 先确认请求本身成功 |
| ② 业务码 | `body["code"] == 0` | 很多系统出错也返 200，靠 body 的 code 区分 |
| ③ 字段值 | order_id/user_id/amount 的值 | 确认数据本身对 |

**最终写出的第 1 条**：

```python
def test_my_1_query_own_order(alice):
    resp = alice.get("/api/orders/O1001")
    assert resp.status_code == 200, alice.pretty(resp)
    assert resp.json()["code"] == 0
    data = resp.json()["data"]
    assert data["order_id"] == "O1001"
    assert data["user_id"] == 1
    assert data["amount"] == "199.00"
```

## 三、今天踩的两个小错

1. **`assert body["code"] == 0, print(...)` 是错的**。
   - `assert 条件, 提示` 里逗号后面是"失败时显示的消息"，不是"要执行的代码"。
   - 写 `print(...)` 会先执行、返回 None，变成 `assert ..., None`，不起提示作用。
   - 正确：直接 `assert body["code"] == 0`，失败时 pytest 会自动显示 `assert 4010 == 0`。

2. **金额 `"199.0"` 写错成 `"199.00"`**。
   - 金额是字符串，逐字符比较，`"199.00" != "199.0"`。
   - 字符串金额必须精确，这是 `test_refund.py` 注释强调过的坑。

## 四、skip / xfail 的"装饰器写法 vs 函数写法"

| 功能 | 装饰器（贴函数头） | 函数调用（写在函数体） |
|---|---|---|
| 参数化 | `@pytest.mark.parametrize` | （无此写法，`pytest.param` 只是包装参数） |
| 预期失败 | `@pytest.mark.xfail` | `pytest.xfail("理由")` |
| 跳过 | `@pytest.mark.skip` | `pytest.skip("理由")` |

**选哪种看"提前知道"还是"跑到才知道"**：
- 装饰器 = 定义时就知道，提前贴标签
- 函数调用 = 运行到某一步才知道，动态执行

**关键区别**：
- 装饰器 `@pytest.mark.xfail`：用例**照常跑完**，跑完失败了算 xfailed、通过了算 XPASS。
- 函数体 `pytest.xfail("理由")`：跑到那一行**立刻停**，直接标记 xfailed，后面代码不执行（和 `pytest.skip()` 一样是"这里打住"）。

## 五、pytest.xfail() 用在函数体的场景

"跑到一半才知道这条该算预期失败"的场景：

1. **按环境**：生产环境有已知 bug，测试环境没有
2. **按资源状态**：订单被别的用例退过了，这条没法重复退（数据污染的优雅处理）
3. **按版本**：v1.x 有 bug，v2.0 已修复

示例：

```python
def test_退款(订单状态):
    if 订单状态 == "已退款":
        pytest.xfail("订单已被退过，无法重复退款")
    resp = 发起退款()
    assert resp.status_code == 200
```

## 六、assert 的"失败提示"机制

`assert 条件, 补充信息`：
- 默认 pytest 会自动显示 `assert 400 == 200`
- 逗号后面的"补充信息"（如 `alice.pretty(resp)`）是"失败时额外打印完整响应"，帮你一眼看出"为什么失败"（服务端的 message 字段才是原因）
