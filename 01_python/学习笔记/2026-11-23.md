## 二、第 2 条：参数化鉴权失败

### 用到的知识点

**`pytest.param(值1, 值2, ..., id="名字")`** —— 给每组参数化数据起个可读的名字。

```python
@pytest.mark.parametrize(
    "token, with_auth, expected_code",
    [
        pytest.param(None, False, 4011, id="不带Authorization头"),
        pytest.param("not-a-real-token", True, 4012, id="假token"),
        pytest.param("expired-token", True, 4012, id="不存在的token(等同过期)"),
    ],
)
def test_my_2_reject_bad_token(client, token, with_auth, expected_code):
    ...
```

- `parametrize` 声明三个参数名，下面每组数据按顺序对应。
- 没有 `id` 时，用例名会显示成 `[None-False-4011]` 这种鬼名字；加了 `id` 就清晰可读。

### `with_auth` 是什么（复习）

`client` 发请求时的开关，控制"这次带不带 token"：

- `with_auth=True`（默认）：带上 `Authorization` 头
- `with_auth=False`：不带 token（用来测"没凭证"场景，或调登录接口本身）

三组数据里，只有第一组用 `False`（模拟"整个头都没有"），后两组用 `True`（有头但 token 内容错）。

### 业务码为什么分 4011 和 4012

- `4011` = 根本没带 token（缺 Authorization 头）
- `4012` = 带了 token，但它是假的/无效的

"没带"和"带了但不对"是两个不同层次的错误，服务端分别返回不同业务码。

### 踩的坑：反向用例状态码写反

第 2 条是"反例"，测的是"token 不对必须被拒"，所以断 `401`，不是 `200`。
正向用例断成功码（200），反向用例断拒绝码（401/400/403）。

## 三、第 3 条：Schema 契约断言

```python
def test_my_3_order_schema(alice):
    resp = alice.get("/api/orders/O1003")
    assert resp.status_code == 200, alice.pretty(resp)
    body = resp.json()
    assert_schema(body, SUCCESS_ENVELOPE, "校验订单接口响应体格式")
    assert_schema(body["data"], ORDER_DATA, "校验订单接口数据内容")
    assert body["data"]["status"] == "PAID"
```

- 两层校验：先查"外壳"（code/message/data），再查"数据本体"（order_id/amount/status）
- 最后补一个值断言，证明不光是结构对、业务值也对

### 踩的坑 1：`assert assert_schema(...)` 多写了 assert

`assert_schema` 名字里带 assert，内部自己会 `raise AssertionError`，**直接调用即可，不能在外面再套 `assert`**。

### 踩的坑 2：import 要补

文件原来只 `import` 了 `ORDER_DATA` 和 `assert_schema`，第 3 条要用 `SUCCESS_ENVELOPE`，得手动补进去。

## 四、`assert` vs `raise`（复习，今天第 3 条踩坑的根源）

| | 作用 | 写法 |
|---|---|---|
| `assert` | 检查条件，不对就抛 `AssertionError` | `assert 条件` |
| `raise` | 主动抛错误，无条件中断 | `raise 异常("说明")` |
| `assert_schema(...)` | 校验结构，内部自己 raise | 直接调用，不加 assert |

一句话：`assert` 是"问一句对不对"，`raise` 是"喊一嗓子出事了"，`assert_schema` 是"已经把这两件事都做好的现成工具"。

---

## 五、关于装饰器 vs 函数调用（之前问的，归纳）

同一个功能往往有两种写法：

| 功能 | 装饰器（贴函数头上） | 函数调用（写函数体里） |
|---|---|---|
| 参数化 | `@pytest.mark.parametrize(...)` | 无（只有 `pytest.param` 包装单组参数） |
| 预期失败 | `@pytest.mark.xfail(...)` | `pytest.xfail("理由")` |
| 跳过 | `@pytest.mark.skip(...)` | `pytest.skip("理由")` |

选择标准：提前知道 → 装饰器；跑到才知道 → 函数调用。
注意 `pytest.parametrize` 这个"函数写法"不存在，参数化只能靠装饰器。

## 七、Git 分支与 PR（11/23 后半段）

### 为什么要分支

`main`（主分支）要**随时能跑、能发版**。如果每个人都在 main 上直接改，main 就永远是"半成品"。

分支 = 一条独立的"工作线"。在分支上随便改、随便测，不影响 main；改完测过，再合并回 main。

类比：main 像"生产环境"，分支像"测试环境"。没人会在生产环境上直接改代码。

### 分支、merge、PR 的关系

- **分支**：干活的独立线
- **merge**：把分支合回 main 的动作
- **PR（Pull Request）**：在 GitHub 上"请求审核后合并"的变更单，团队里是代码审查的载体

### 完整流程（今天亲手走通的）

```
git switch -c feat/my-cases    # 建分支并切过去
# 在分支上改代码
git add 文件                   # 暂存
git commit -m "..."            # 提交
git switch main                # 切回 main
git merge feat/my-cases        # 合并
# 跑测试验证 5 passed 还在
```

### 今天踩的坑（最重要的一条）

**没 commit 的改动，不属于任何分支，切分支时"跟着你走"。**

| 状态 | 属于分支吗 | 切分支时会怎样 |
|---|---|---|
| 改了但没 commit | ❌ | 跟着你走，切到哪都还在 |
| 改了且已 commit | ✅ | 留在原分支，切走就"消失" |

所以正确顺序是：**先 commit，再切分支**，改动才会真正"落到当前分支"。

### 其他要点

- 分支名要写全：`feat/my-cases`，不能只写 `feat`（`git switch feat` 会报 invalid reference）
- 命令是 `git switch -c`（不是 `git -switch`），`-c` = 创建新分支，不能省
- `Fast-forward` 合并 = 分支只是 main 的"前进版"、没分叉，直接把指针快进，最省事
- 本地领先远程 11 个 commit，还没 push（明天接 CI 时要 push）
