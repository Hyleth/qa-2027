
## 二、核心概念：xfail 与 strict

- `xfail` = 给「已知会红的用例」贴标签，让它红得合理、不拖累整体。
- `strict=True` = bug 修好后用例变绿，但标签还贴着，pytest 故意报 XPASS（算失败），逼你回来摘标签。
- `strict=False`（默认）= 贴了标签的用例无论红绿都"睁一只眼闭一只眼"，坏处是 bug 修好了也没人记得摘标签，一直"假绿"。

**记住两种"红"**：
- `FAILED`（普通红）= 真出错，要修
- `XPASS(strict)`（这种红）= bug 修好了但忘了摘标签，是"信号"不是"错误"

## 三、pytest.mark 是一类标签，不是一种

| mark 类型 | 作用 | 项目里的例子 |
|---|---|---|
| `@pytest.mark.parametrize` | 参数化（数据驱动用这个） | `test_refund.py` 第 48 行 |
| `@pytest.mark.xfail` | 标记"预期失败" | `test_orders.py` 第 51 行 |
| `@pytest.mark.skip` | 标记"跳过" | `my_cases` 里后面会见到 |

**数据驱动 ≠ 加 mark**。数据驱动靠的是 `parametrize` 这一个特定标签，`pytest.mark` 是"标签"这一大类的总称。

## 四、两个 bug 的修复

### BUG-01：负数退款没被拦

在 `mock_server.py` 退款逻辑里，`if amount_dec > ...` 之前加：

```python
if amount_dec <= 0:
    self._fail(400, 4001, "退款金额必须大于 0")
    return
```

`return` 很关键——不加的话代码会继续往下走，最后还是会退款成功。

### BUG-02：查订单没校验归属（越权）

在 `mock_server.py` 查订单逻辑里，`self._ok(order)` 之前加：

```python
if order["user_id"] != user_id:
    self._fail(403, 4030, "无权查看他人的订单")
    return
```

### 摘标签的位置不同（今天的关键理解）

| bug | 用例类型 | xfail 标签在哪 | 摘标签删什么 |
|---|---|---|---|
| BUG-01 | 数据驱动（yaml） | yaml 里的 `known_bug: BUG-01` | 删 yaml 那一行 |
| BUG-02 | 普通函数 | 函数上的 `@pytest.mark.xfail` | 删装饰器 |

## 五、越权是什么（真实项目漏测率最高的 bug）

- 越权 = 用 A 的身份访问到 B 的数据（alice 查到 bob 的订单）。
- 它**不报错**，接口正常返回 200、数据正常给，只是悄悄泄露数据——所以最容易被漏测。
- 测它靠"反向用例"：期望返回 403，而不是正向的 200。

## 六、-k 筛选用例的坑（今天踩了两次）

`-k` 匹配的是用例的"名字"（函数名 + 参数化标题），不是"内容"。

| 筛法 | 结果 | 原因 |
|---|---|---|
| `-k 负数` | ❌ 0 selected | 中文在终端有编码问题 |
| `-k REF-04` | ✅ | id 被拼进参数化标题里 |
| `-k O1002` | ❌ 0 selected | O1002 在函数体内，不在函数名里 |
| `-k other_users` | ✅ | other_users 在函数名 `test_query_other_users_order_is_rejected` 里 |

**规律**：数据驱动用例用 id（REF-04）筛；普通函数用函数名里的英文词筛。

## 七、数据驱动 vs 普通函数（复习）

- **数据驱动**：数据在 yaml，一个函数循环跑。名字长这样 `test_refund_by_data[REF-04-标题]`。加用例只改 yaml。
- **普通函数**：数据写死在函数里。名字就是函数名。每个用例一个函数。
- 区分标准：用例"长得很像、只是数据不同"→ 数据驱动；逻辑差异大 → 普通函数。
