# 2026-11-12 学习笔记 · parametrize 与数据驱动

> 一句话主题：**"测什么"（数据）和"怎么测"（逻辑）分开**，`parametrize` 负责把一组数据自动变成一组用例。

---

## 一、核心一句话（面试必背）

**数据驱动 = 测试逻辑只写一份，测试数据单独放，用 `@pytest.mark.parametrize` 把每组数据自动展开成一条独立用例。**

为什么不用自己写 `for` 循环：

| | 自己写 for 循环 | 用 parametrize |
|---|---|---|
| 一组数据失败 | 整个用例变红，后面的数据不再跑 | **只有这一条红，其他照常跑** |
| 报告里算几条 | 1 条 | **每组数据 1 条，单独计数、单独显示** |
| 失败定位 | 看不出是哪组数据挂的 | 用例名直接告诉你哪组 |

这就是 parametrize 最大的价值：**一条失败不影响其他条，报告里每条数据都能单独看见。**

---

## 二、基础语法（就记这三个参数）

```python
@pytest.mark.parametrize(argnames, argvalues, ids=None)
```

| 参数 | 是什么 | 例子 |
|---|---|---|
| `argnames` | 参数名，一个或一串 | `"username"` 或 `["username", "password"]` |
| `argvalues` | 数据列表，每个元素是一组值 | `["admin", "test"]` 或 `[("admin","123"), ...]` |
| `ids` | 给每组数据起个可读名字（可选） | `ids=["正常登录", "密码错误"]` |

---

## 三、三种写法对照（今天搞懂的核心）

### 写法 1：一个参数，传多个值

```python
@pytest.mark.parametrize(
    "username",
    ["admin", "test", "guest"],
)
def test_user(username):
    print(username)
```

生成 3 条：`test_user[admin]`、`test_user[test]`、`test_user[guest]`。

### 写法 2：多个参数，用元组组合

```python
@pytest.mark.parametrize(
    ["username", "password"],
    [
        ("admin", "123"),
        ("test", "pass"),
    ],
)
def test_login(username, password):
    print(username, password)
```

每个元组按位置对应参数，2 条用例，每条拿到一对 `(用户名, 密码)`。

### 写法 3：一个参数，值是字典（教材的写法）

```python
@pytest.mark.parametrize(
    "case",
    [{"id": "LOGIN-01", "title": "正确登录"}, {"id": "LOGIN-02", "title": "密码错误"}],
)
def test_by_data(case):
    print(case["id"], case["title"])
```

**整个字典是 `case` 这个参数的值**，函数里用 `case["id"]` 取值。

---

## 四、关键点：参数名 vs 数据值，别搞混

这是今天最容易踩的坑，记死这一句：

> **`parametrize` 的第一个参数是"参数名"，后面列表里的每个元素是"这个参数的值"。元素是字符串、元组、字典都行，取决于你想给参数传什么。**

- 想让字典的 key 当参数名 → **错**。`parametrize("username", [{"admin":"123"}])` 会把 `admin` 当参数名，和 `username` 对不上，报错。
- 想让字典整体当"一个参数的值" → **对**。`parametrize("case", [{"id":"1"}])`，函数写 `def test(case)`，`case` 就是整个字典。

---

## 五、教材里的完整链路（11/12 合格线）

```python
CASES = yaml.safe_load(Path(__file__).parents[1] / "data" / "cases.yaml").read_text(encoding="utf-8")
LOGIN_CASES = CASES["login"]

def _ids(case):
    return f"{case['id']}-{case['title']}"

@pytest.mark.parametrize("case", LOGIN_CASES, ids=_ids)
def test_login_by_data(client, case):
    resp = client.post("/api/login", case["request"], with_auth=False)
    # 后面用 case["expect"] 做断言
```

逐步走一遍：

1. `yaml.safe_load` 读 YAML → 得到嵌套字典 `{"login": [...], "orders": [...]}`
2. `CASES["login"]` → 取出 login 这组，就是 **5 个字典的列表**（`[{}, {}, ...]`）
3. `parametrize("case", LOGIN_CASES)` → 5 个字典变成 5 条用例
4. 函数里 `case["request"]` 取发送数据、`case["expect"]` 取期望结果
5. `ids=_ids` → 每条用例显示成 `LOGIN-01-正确的用户名密码可以登录`

**`LOGIN_CASES` 就是 `[{},{}]` 这种形式**——你今天的理解是对的。

YAML 里一条用例有三个关键字段：

| 字段 | 含义 |
|---|---|
| `request` | 发送给接口的数据 |
| `expect` | 期望返回的结果（状态码、业务码） |
| `known_bug` | 已知 bug，标了就把这条变成 xfail |

## 六、known_bug 怎么变成 xfail（11/12 的第三小步）

`test_refund.py` 里的 `_params()` 会把 `known_bug` 字段转成 `pytest.param(..., marks=pytest.mark.xfail(...))`，让"已知会挂"的用例不报失败、而是显示 XFAIL。那 2 条 XFAIL（BUG-01 负数退款、BUG-02 越权查单）就是这么来的。

---

## 七、三件套：pytest.param / marks / pytest.mark.xfail

先分清三个东西各是什么：

| 名字 | 是什么 | 一句话 |
|---|---|---|
| `pytest.mark.xfail(...)` | 一个**标记**，表示"这条预期会失败" | "我知道它会红，先标好，别算我失败" |
| `pytest.param(...)` | 一个**包装器**，包住"一组参数化数据" | "我要给这一组数据单独加东西" |
| `marks=...` | `pytest.param()` 的一个**参数**，往里塞标记 | "把 xfail 标记塞到这一组数据上" |

关系：**`pytest.param()` 用 `marks=` 把 `pytest.mark.xfail()` 套在某一组数据上**，达到"只让这一条 xfail，别的正常跑"。

### 关键区分：failed vs xfailed

- `failed`：真失败，要修
- `xfailed`：预期失败，提前标记，**不算失败**

### 两种标记位置的对比（最重要）

同一个 `xfail`，放不同位置，作用范围完全不同：

```python
# 方式 A：放在函数上面 → 所有参数组全部 xfail
@pytest.mark.xfail(reason="整个接口没开发完")
@pytest.mark.parametrize("u", ["a", "b", "c"])
def test(u):
    ...

# 方式 B：放在 pytest.param 的 marks 里 → 只标记这一条数据
@pytest.mark.parametrize("u", [
    "a",
    pytest.param("b", marks=pytest.mark.xfail(reason="这条是bug")),
    "c",
])
def test(u):
    ...
```

| | 放哪 | 影响范围 |
|---|---|---|
| 方式 A | 装饰器在函数上 | 所有参数组 |
| 方式 B | `pytest.param(marks=...)` | 只这一条 |

教材的 `test_refund.py` 用的是**方式 B**——因为 5 条退款里只有 1 条（负数退款）是 bug。

### 记忆钩子

> `xfail` 是"标记"，`param` 是"包装"，`marks=` 是"把标记塞进包装的那条数据里"。

`xfail` 后面那堆参数（`condition`/`raises`/`run`/`strict`）今天不用碰，等自己写框架时再查。

## 八、_params() 逐行解读（教材原文）

```python
def _params():
    params = []
    for case in REFUND_CASES:
        marks = ()                    # ① 默认：空元组 = 不打任何标记
        if case.get("known_bug"):     # ② 如果这条有 known_bug 字段
            marks = (
                pytest.mark.xfail(
                    reason=f"{case['known_bug']}：{case['title']}（服务端已知缺陷）",
                    strict=True,
                ),
            )
        params.append(
            pytest.param(case, marks=marks, id=f"{case['id']}-{case['title']}")
        )                            # ③ 每条都包进 pytest.param，统一设置 id
    return params
```

**核心结论：5 条用例都包进了 `pytest.param()`，但只有 `known_bug` 那条的 `marks` 里装了 xfail 标记，另外 4 条的 `marks` 是空元组 `()` = 没打任何标记 = 正常用例。**

### 逐条看 `marks` 怎么变

| case | 有 `known_bug` 吗 | `marks` 的值 | 结果 |
|---|---|---|---|
| REF-01 正常退款 | 无 | `()` 空元组 | 正常用例 |
| REF-02 超额退款 | 无 | `()` | 正常用例 |
| REF-03 重复退款 | 无 | `()` | 正常用例 |
| **REF-04 负数退款** | **有** | `(xfail标记,)` | **xfail 用例** |
| REF-05 缺字段 | 无 | `()` | 正常用例 |

### 两个易错点

1. **`marks=()` 不是"空的 xfail 标记"，是"没有任何标记"**。正常用例压根没创建 xfail 标记，它们的"标记口袋"是空的。
2. **为什么每条都包 `pytest.param()`，而不是只包 bug 那条？** 因为要**统一给每条设置 `id`**（`f"{id}-{title}"`）。如果正常用例直接塞裸字典，就没法单独起 id 了。所以 `pytest.param()` 在这里有两个作用：① 统一设置 id；② 给已知 bug 那条单独塞 xfail。

### `case.get("known_bug")` 为什么用 get 不用 []

`case.get("known_bug")` 是"取这个字段，没有就返回 `None`"。

- YAML 里正常用例**根本没写 `known_bug` 字段**，不是"有但为空"
- 所以正常用例 `case.get("known_bug")` 返回 `None`，`if None` 是假，跳过 if，`marks` 保持 `()`
- 只有 REF-04 那条 YAML 里真写了 `known_bug`，才进 if 装 xfail

这是 W1 D2 学的 `dict.get(k, 默认值)` 的实战用法——安全地取一个可能不存在的字段，避免 `case["known_bug"]` 直接 KeyError。
