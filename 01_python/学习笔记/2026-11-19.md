# 学习笔记 · 2026-11-19（周四）

> 主题：JSON Schema —— 守住接口返回的结构（11/14 的内容，因进度偏移调到今天学）

## 一、今天解决的核心问题

昨天学会了"值断言"（`assert body["code"] == 200`），今天补上它的盲区：

- **值断言**只能"伸手去摸字段，确认值对不对"，但它不知道"这个接口本该有哪些字段"。
- 如果开发改了字段名 / 删了字段，值断言只会报模糊的 `KeyError`，你分不清是"业务错"还是"契约变"。

**JSON Schema 的思路**：跑测试前，先把"接口返回必须有哪些字段、什么类型、什么格式"写成一份规则文件。谁不按规则来，当场报警、报人话。

> **一句话（合格线）**：值断言管"值对不对"，schema 管"结构还在不在"。两个都要有，不能互相替代。

## 二、核心概念：两层校验

一个接口的返回是"壳 + 肉"两层：

```
body（整个返回）
 ├─ code / message / data   ← 壳（外壳模板管）
 └─ data 里装的东西          ← 肉（数据模板管）
```

所以 `test_orders.py` 里 `assert_schema` 要**调两次**：

```python
assert_schema(body, SUCCESS_ENVELOPE, "订单响应外壳")   # 查壳
assert_schema(body["data"], ORDER_DATA, "订单响应 data")  # 查肉
```

## 三、几个关键词

| 关键字 | 作用 | 例子 |
|---|---|---|
| `type` | 字段必须是某类型 | `"type": "string"` |
| `required` | 列出的字段必须有（守"删字段/改字段名"） | `["order_id", "amount"]` |
| `properties` | 每个字段各自的规则 | 里面再写 type / pattern / enum |
| `additionalProperties: False` | 规则外的字段不许出现（守"多加字段"） | 报 "Additional properties are not allowed" |
| `pattern` | 字符串要匹配的格式（正则） | `r"^\d+\.\d{2}$"` = 像 199.00 |
| `enum` | 只能从几个固定值里选 | `["PAID","REFUNDED","CANCELLED"]` |
| `minLength` / `minimum` | 最短长度 / 最小值下限 | token≥8、code≥1 |

## 四、`assert_schema` 函数在干什么（本次读代码搞懂的）

```python
def assert_schema(payload, schema, label="响应体"):
    errors = validate(payload, schema)   # 第1步：拿规则查数据，问题放进 errors 列表
    if errors:                            # 有问题才往下走
        raise AssertionError(...)         # 第2步：拼人话报错，抛异常让测试失败
```

- 它自己不"检查"（那是 `validate` 干的，底层是第三方库 jsonschema），它负责"检查完有问题 → 把话说清楚 → 报错"。
- 三个参数：要查的数据、结构规则、报错时的名字。

## 五、两把锁：required vs additionalProperties

`ORDER_DATA` 里有两个东西同时守结构：

- **锁1 `required`**：该有的字段"缺了没有" → 缺了报 `is a required property`
- **锁2 `additionalProperties: False`**：不该有的字段"多出来没有" → 多了报 `Additional properties are not allowed`

**实测验证**（今天亲手做的实验）：

1. 把 `required` 里的 `"amount"` 删掉 → 跑测试报 `Additional properties are not allowed ('amount' was unexpected)`
   - 原因：删掉后 amount 变成"规则外字段"，被锁2拦住。说明两道锁互相兜底。
2. 反向实验（可选）：给 `required` 加一个不存在的 `total_price` → 报 `'total_price' is a required property`

## 六、字段被改，前端"一定会报错吗"？（今天最有价值的一问）

**不一定。分四种情况：**

| 开发干了什么 | 前端会不会崩 | 谁来守 |
|---|---|---|
| 改字段名 amount→total_amount | 必崩（前端取不到，白屏） | `required` |
| 改类型 "199.00"→199.0 | 不一定崩，埋隐蔽坑（`===` 判断、浮点精度） | `"type"` |
| 删字段 | 大概率崩 / 逻辑全错 | `required` |
| 加字段 | 一般不崩，但是"契约变了"的信号 | `additionalProperties: False` |

**核心结论**：崩不是唯一坏结果。有的崩（改字段名/删字段），有的不崩但悄悄烂（改类型），有的不崩但是危险信号（加字段）。**schema 的价值恰恰是抓住后两种**——值断言 100% 抓不到，等变线上事故就晚了。

## 七、关于"写不出来"的焦虑（重要）

今天反复纠结"自己写不出来"。结论：

- **今天目标不是"自己写"，是"会调用"**。`assert_schema` 函数和那些规则都是现成的，你负责 `assert_schema(body, SUCCESS_ENVELOPE, "名字")` 这样调用即可。
- **schema 不是凭空发明的，是照接口文档翻译的**。文档写"amount string 两位小数"→ 翻译成 `{"type":"string","pattern":...}`，一行对应一行。到 W3 后期才需要自己动手，到时先给模板练，不凭空写。
- `assert_schema` 这种通用校验函数，真实团队里通常由资深的人写一次、全组复用，你作为使用者只需要会调用。
