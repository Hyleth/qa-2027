# pytest fixture 详细讲解（自动化测试框架版，适合接口 / UI 自动化）

## 一、什么是 fixture

`fixture` 是 pytest 里**用来准备测试前置、清理后置、提供测试数据 / 对象**的函数，用来替代传统 unittest 的 `setup()` / `teardown()`，比 setup 灵活非常多。

> 
> 一句话：fixture = 测试资源 + 前置准备 + 后置清理
> 比如：
> 
> 
> - 前置：创建数据库连接、实例化请求 session、登录获取 token、准备测试数据
> - 后置：关闭数据库、退出登录、清理测试数据

和 unittest setup 的区别：

1. setup 是**每个用例固定执行**，粒度只能是类 / 方法；
2. fixture **按需调用**，想用就传，不想用不跑；支持函数级、类级、模块级、会话级；
3. fixture 可以返回数据，**给用例传参**（最核心优势！）
4. fixture 支持嵌套依赖（fixture 调用另一个 fixture）

---

## 二、基础写法

加装饰器 `@pytest.fixture`，用例参数写这个 fixture 名字，自动注入。

```
import pytest

# 定义fixture
@pytest.fixture()
def my_data():
    # 前置代码
    print("\n===== fixture 前置：准备数据 =====")
    data = {"username": "test", "pwd": "123456"}
    # 返回值，给测试用例接收
    return data

# 测试用例：参数名字和fixture名字一致，自动调用
def test_demo(my_data):
    print("用例拿到的数据：", my_data)
    assert my_data["username"] == "test"
```

0运行成功，但未检测到输出内容

运行：`pytest test_xxx.py -v -s`

> 
> `-s` 可以打印里面的 print 内容

### 后置清理（yield 重点！自动化必用）

`yield` 前面是**前置**，yield 之后是**后置**

```
@pytest.fixture()
def db_conn():
    print("前置：连接数据库")
    conn = "数据库连接对象"
    yield conn   # 把连接传给用例
    # 用例执行完之后，才走到下面
    print("后置：关闭数据库连接")

def test_db(db_conn):
    print("用例使用：", db_conn)
```

执行顺序：
`fixture前置 → 执行test用例 → fixture后置`

> 
> 如果你不用 yield，只用 return：**没有后置清理**

## 三、fixture 作用域 scope（高频考点，自动化框架必背）

`@pytest.fixture(scope="xxx")`
scope 可选值：

表格

| scope | 说明 | 执行时机 |
| --- | --- | --- |
| `function`（默认） | 函数级 | **每个测试用例，都会跑一次 fixture** |
| `class` | 类级 | 一个测试类里，**所有用例总共只跑 1 次** |
| `module` | 模块级 | 一个 py 文件（模块），全部用例只跑 1 次 |
| `session` | 会话级 | 整个 pytest 执行过程（所有文件）**只跑 1 次**（适合全局登录、全局 session） |

示例：全局只登录一次（session 级，接口自动化最常用）

```
@pytest.fixture(scope="session")
def login_token():
    print("==== session级：只登录一次 ====")
    token = "abc123456token"
    yield token
    print("==== session后置：退出登录 ====")

def test_case1(login_token):
    print(f"case1 使用token：{login_token}")

def test_case2(login_token):
    print(f"case2 使用token：{login_token}")
```

👉 两个用例，login 只执行一次！

## 四、fixture 依赖（fixture 调用 fixture）

fixture 可以直接传别的 fixture 当参数，实现嵌套

```
@pytest.fixture()
def base_url():
    return "http://127.0.0.1:8080/api"

@pytest.fixture()
def req_session(base_url):
    import requests
    s = requests.Session()
    print(f"session初始化，基础地址：{base_url}")
    yield s
    s.close()

def test_api(req_session, base_url):
    url = base_url + "/login"
    res = req_session.get(url)
    assert res.status_code == 200
```

> 
> req_session 依赖 base_url，自动先执行 base_url

## 五、fixture 参数化（params）

fixture 自带 params，给 fixture 循环传入多组数据，**所有用例自动循环跑多组**

```
@pytest.fixture(params=[
    {"user": "admin", "pwd": "123456"},
    {"user": "test", "pwd": "654321"},
])
def user_info(request):
    # request.param 拿到当前这一组参数
    return request.param

def test_login(user_info):
    print("当前账号：", user_info)
    assert user_info["pwd"] != ""
```

这个用例会自动跑 2 次，两组数据分别执行。
## 七、return 和 yield 两种写法对比

1. `return`：只提供资源，**没有后置**

```
@pytest.fixture()
def demo():
    return 123
```

2. `yield`：前置 + 给用例返回值 + 后置清理（自动化首选）

```
@pytest.fixture()
def demo():
    print("前置")
    yield 123
    print("后置")
```
## 八、conftest.py（重点！框架分层必备）

> 
> `conftest.py`：pytest 专属配置文件，**专门放 fixture**
> 规则：

1. 不需要 import！同目录 / 子目录的用例，直接调用里面的 fixture
2. 可以多层：根目录 conftest（全局 fixture）、各个模块文件夹单独 conftest
3. 适合放：登录 token、全局 session、数据库连接、公共前置

目录示例（接口自动化标准结构）

```
project/
├── conftest.py        # 全局fixture：session、登录token
├── test_login.py
├── test_user.py
└── test_order.py
```

conftest.py 里面写好 login_token，所有 test_*.py 直接用，不用 import。

## 九、常见面试题 & 容易踩坑点

### 1. fixture 和 setup 的区别

- setup：绑定在类 / 方法，固定执行，不能传参，不能跨文件共享
- fixture：按需加载、可传参、支持多作用域、可放 conftest 全局共享、支持后置清理

### 2. scope=session 注意点

session 级 fixture，**整个 pytest 运行期间只执行一次**，适合登录、全局 session；
⚠️ 不要在 session fixture 里面写每个用例都要清理的数据。

### 3. 执行顺序总结

autouse 的 fixture → 显式传入的 fixture（依赖顺序） → 测试用例 → 后置（逆序执行）

### 4. 坑：fixture 名字不要和变量重名

不要用内置关键字、不要和测试函数重名。

### 5. 坑：yield 后面代码，就算用例报错，依然会执行！

✅ 这是 fixture 一大优点：**用例失败，后置清理照样跑**（数据库关闭、释放资源不会漏）

## 十、完整自动化框架常用组合示例（接口自动化）

conftest.py

```
import pytest
import requests

@pytest.fixture(scope="session")
def base_url():
    return "http://xxx/api/v1"

@pytest.fixture(scope="session")
def session(base_url):
    s = requests.Session()
    # 前置：登录
    login_data = {"username":"admin","password":"123456"}
    res = s.post(base_url + "/login", json=login_data)
    token = res.json()["token"]
    s.headers["Authorization"] = f"Bearer {token}"
    yield s
    # 后置：退出登录，关闭session
    s.post(base_url + "/logout")
    s.close()
```

测试用例 test_user.py

```
def test_get_user_list(session, base_url):
    resp = session.get(base_url + "/user/list")
    assert resp.status_code == 200
    assert resp.json()["code"] == 0
```

## 十一、今天（11/11）实际搞懂的问题（比通用教材更该记）

### 1. `session` 和 `client` 是什么（大白话版）

- `fixture` = 测试前的准备工作，写成代码让 pytest 自动做
- `session` 和 `client` 是两个具体 fixture 的名字：
  - `base_url`（scope=session）= 起服务，整个测试只做一次
  - `client`（scope=function）= 造一个"能发请求的客户端"，每条用例造一个
- 对应手工测试：起服务、打开 Postman、发请求、看结果

### 2. "起服务"对应手工测试的什么（我的知识盲区）

- 手工测试里我**没做过"起服务"**，因为服务是开发/运维起好的，我直接用
- 自动化测试里要**自己起一个"假后端"（mock）**，因为：
  1. 手上没有真实后端
  2. 要隔离环境、结果稳定
  3. 面试要考"能自己搭一套"
- `mock_server.py` = 用 Python 写的假后端，几百行，模拟登录/退款接口

### 3. `server, url = serve_in_background()` 是什么

- 一次返回**两个值**：`server`（假服务对象，能关掉）+ `url`（服务地址如 127.0.0.1:8000）
- Python 里 `a, b = 函数()` 就是"一次接住两个返回值"，W1 没练过这个写法

### 4. 真实工作 vs 教材 mock 的区别

| | 真实工作 | 教材（学习阶段） |
|---|---|---|
| 服务谁起 | 开发/运维 | 自己的 mock_server.py |
| 服务在哪 | 测试环境（远程） | 本地 127.0.0.1:8000 |
| 拉不拉后端代码 | 不拉 | 不需要，mock 是假后端 |
| base_url 指向 | http://test-api.xxx.com | 127.0.0.1:8000 |
| 用例代码 client.post(...) | 完全一样 | 完全一样 |

**关键结论**：入职后把 `base_url` 改成公司测试环境地址，这套框架原样能用。

### 5. 真实环境还用不用 `scope="session"`？（纠正误区）

**用，而且更重要。** 关键纠正：`scope="session"` 的意思**不是"起服务"**，而是"**整个测试会话只做一次**"。

真实环境里服务是别人起好的，不用我起，但照样有一堆"只做一次"的事靠 session 级 fixture：
- 登录拿一个管理员 token（登一次，几十条用例共用）
- 连数据库、建连接池
- 读全局配置文件
- 准备公共测试数据

**记忆钩子**：scope 回答"做几次"——session = 做一次（贵/共用的东西），function = 每条做一次（要干净的身份）。
